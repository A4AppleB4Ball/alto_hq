## Goal

Every stage has checks over stored state, per company, that give one
structured verdict (check id, subject, pass / fail / unavailable / waived, a
fixed reason, evidence). Each check is proved on real frozen cases before it
is trusted, and releases are compared live vs candidate on a frozen snapshot.
QA, ops and dev use these instead of writing their own scripts.

## Stories

1. Freeze a company's stored state into a case (manifest, hashes; read-only on live) — next
2. First cases: ARSSBL, CHANDAN, one healthy company; then the other 8 of I-20261015-1058 — next
3. Expected verdicts per case — idea
4. Case runner: every check over every case vs expected verdicts — idea
5. Verdict contract, check catalogue and one command (`python -m backend.validation run`) — idea
6. Stage invariants (ingestion, index, intake, quarterly completeness, stance chain, proposal, execution), each proved on cases — idea
7. Chain completeness with explicit states: analysed, pending, blocked (reason), unavailable at source (evidence, recheck date) — idea
8. Release runner: live vs candidate on a golden snapshot, stage-by-stage changes; LLM replay / qwen tiers — idea (needs T-20261015-0321-checkout-data-root)
9. Ship refuses a release without a passing report — idea
10. Verdict validity: each verdict carries check version, as-of, input fingerprint and run id; stale is its own state; a nightly full rebuild is compared with the incremental table; decisions re-check at decision time — idea (spike question B8)

## Open questions

**Where verdicts can drift from the stores or the world** (session,
2026-10-15). A verdict is a derived cache, rebuildable from the stores; it
never leads (`backend/docs/40_contracts.md`).

| # | Drift | How it is caught |
|---|---|---|
| 1 | Store changes after the check | verdict stores a fingerprint of the records it read; mismatch = stale |
| 2 | Writes outside the pipeline (scripts, worktree symlink, Sync Data, stance checkout) | fingerprint on read; nightly full rebuild diffed against the incremental table |
| 3 | Check logic changes | check id + version on every verdict; new version invalidates |
| 4 | Check derives data differently from the product | checks call the product's contract functions (`DataAccess`, `AsOfLedger`, quarter policy); proved on frozen cases |
| 5 | Missing subjects (new watchlist company) | subjects come from the watchlist version the product used; no verdict = fail "not checked" |
| 6 | The validation run itself fails | a verdict run per day is required; missing or partial run = fail |
| 7 | Partial runs leave rows of mixed age | run id and computed_at per row; older than the company's last product run = stale |
| 8 | Expectation moves while data does not (a quarter falls due) | completeness is per as-of date, recomputed daily; "due" from evidence (results calendar, board-meeting intimations) |
| 9 | Store vs the world (a filing exists that we never fetched) | "unavailable" needs evidence (where, when) and a recheck date; second source later (NSE/BSE/Screener, web agent). Bounded, not closed |
| 10 | Mac vs server (server trades on its synced copy; HEAD stays behind origin) | the proposal records the stance versions it used; a server-side check compares them with the fingerprints the Mac verified |
| 11 | Waivers outlive their condition | waiver bound to a fingerprint and an expiry; reopens when evidence changes |
| 12 | The cache starts deciding (proposal reads the table, not the store) | money-moving steps re-run their checks on their own inputs; the table serves the brief and triage only |

Happening today: #12 (the proposal checks staleness only, how ARSSBL was
bought) and #10 (nothing checks what the server actually traded on).
